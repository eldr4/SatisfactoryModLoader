# Satisfactory UEVR Enhancements Input Initialization Investigation

## Purpose

This document is the compact handoff and execution brief for diagnosing and
patching Quest 2 controller input initialization in the Satisfactory mod
"UEVR Enhancements". It supersedes the verbose environment-setup discussion.

The development environment is now operational. Continue from the preservation,
source matching, baseline build, and diagnostic stages. Do not repeat completed
software-installation work unless a concrete build error requires it.

## Goal

Fix the handoff between the active UEVR Lua profile and the game-side UEVR
Enhancements bridge so that:

1. Lua initialization completes without an FString argument error.
2. The bridge performs its complete native initialization, including the
   UEVRBridgeInitialised event broadcast.
3. Quest 2 controller buttons, triggers, and sticks work consistently.
4. Left-stick movement is centered and normal.
5. Right-stick turning is normal.
6. HMD or controller pose changes do not create locomotion or circular movement.
7. The result works after two consecutive complete game/UEVR restarts.

Removal of the Lua exception alone is not success.

## Primary Hypothesis and Alternatives

Primary hypothesis to test:

UEVR's Lua-to-Unreal reflected call layer fails to marshal the two-FString
InitUEVRBridge signature in this combination of Satisfactory 1.2, SML 3.12,
UEVR Enhancements alpha3, the active profile, and current UEVR.

Do not treat this as proven. Alternatives include:

- Native mod and Lua profile revision mismatch.
- Installed runtime reflection metadata differs from source.
- UEVR regression affecting multiple FString parameters.
- A reflected parameter has unexpected CPF_OutParm or related flags.
- Lua resolves a wrapper or wrong/stale bridge class/object.
- Multiple bridge objects or Lua callback registrations exist.
- Initialization occurs before player/world readiness or more than once.
- Missing event listeners or stale movement state causes the post-bypass input
  behavior independently of FString marshalling.

## Likely Minimal Final Fix

Only if diagnostics confirm single-FString and no-argument methods work while
the current two-FString method fails, add a backward-compatible split API using
the repository's spelling convention:

  UFUNCTION(BlueprintCallable)
  void SetUEVRProfileVersion(FString Profile);

  UFUNCTION(BlueprintCallable)
  void SetUEVRAPIVersion(FString UEVRVersion);

  UFUNCTION(BlueprintCallable)
  void InitialiseUEVRBridge();

Responsibilities:

- SetUEVRProfileVersion assigns ProfileVersion.
- SetUEVRAPIVersion assigns APIVersion.
- InitialiseUEVRBridge logs stored values, sets IsInitialised, and broadcasts
  UEVRBridgeInitialised exactly once per intended lifecycle.
- Existing InitUEVRBridge remains for backward compatibility and delegates to
  the same initialization path.

Before imposing a permanent IsInitialised guard, inspect whether reinjection in
the same process or world transitions intentionally require reinitialization.
Choose idempotence based on existing lifecycle behavior, not assumption.

Lua should compute a safe dotted API version string, call both single-string
setters, then call the no-argument initializer. Keep the change minimal.

## Input Pipeline Diagnostics

Instrument only as needed and rate-limit logs.

1. UEVR XInput callback: user index, return value, packet, buttons, both stick
   axes, and triggers. Log changes or sample at a controlled interval.
2. Lua forwarding calls: buttons, sticks, and triggers passed to the bridge.
3. Native bridge state: all stored controls and scaled axis values.
4. InputActionsTick: ticking state, valid indices/actions/listeners, and values
   constrained to [-1, 1]. Verify rest returns to approximately zero.
5. Unreal Enhanced Input: mapping context count, target player/controller,
   trigger phases, and absence of a duplicate constant axis source.

Do not add ResetInputState to the final fix unless logs show stale values or
disconnect/reinjection state is a cause.
